# Architecture

Nexara is a monorepo with a FastAPI backend and a Next.js frontend. This page
describes how the parts fit together.

## Backend layering

The backend uses strict layers:

```
api/v1/<router>.py -> services/<x>_service.py -> repositories/<x>_repo.py -> models/<x>.py
```

- **Routes** parse requests, resolve dependencies, and return schemas. Routes
  never import repositories directly.
- **Services** hold business rules, such as permission and visibility checks.
  They receive their repository, the community id, and the session through
  dependency injection from `core/dependencies.py`.
- **Repositories** build SQLAlchemy queries and are the only layer that talks to
  the database. After writes they `flush()` and `refresh()` the session.
- **Models** are SQLAlchemy 2.0 declarative classes using `Mapped[]` and
  `mapped_column`.

Errors are raised as `AppError` subclasses (`NotFoundError`,
`AuthorizationError`, ...) from `core/exceptions.py` and are serialized into a
standard envelope: `{ "error": { "code", "message", "details" } }`. Services
never raise raw HTTP exceptions.

## Database

SQLAlchemy runs in async mode with PostgreSQL 16. JSONB columns store flexible
structures such as RSVP labels and contribution slots. Full-text search uses
computed `TSVECTOR` columns named `search_fts` with GIN indexes; they are
generated by `Computed(...)` rather than triggers.

Migrations are managed by Alembic in a linear chain. Always check
`alembic heads` and set `down_revision` to the current head.

## Multi-tenancy

Every row carries a `community_id`, and every repository query filters on it.
`BaseRepository` adds soft-delete handling (`deleted_at IS NULL`) and
`apply_block_filter(stmt, viewer_id)` for hiding blocked users on
viewer-scoped reads.

## Visibility

Content uses `visibility` of `community`, `subgroup`, or `private`, plus an
optional `subgroup_id`. A service-level `_can_view` check enforces the rules:
community content is visible to all members, private content to its author, and
subgroup content to members of that subgroup. Repositories mirror this logic
with inline `OR` clauses for list queries.

## Realtime and notifications

`services/realtime/events.py` defines `RealtimeEvent`. The `EventBus` fans
events out to Server-Sent Events (`api/v1/sse.py`) and WebSockets
(`api/v1/ws.py`). `NotificationService.notify(user_id, type, ...)` consults each
user's per-channel preferences through `PREF_MAP` and delivers in-app, Web Push,
and email notifications. When you add a notification type, extend `PREF_MAP`.

## Background jobs

Celery handles asynchronous work with these queues: `default`, `maintenance`,
`notifications`, `email`, and `media`. The schedule lives in
`tasks/celery_app.py`. Beat runs as a singleton guarded by a PostgreSQL
advisory lock in `tasks/beat_lock.py`. To add a periodic job, append it to
`beat_schedule` and route the task to the right queue.

## Frontend

The frontend is Next.js 16 with the App Router and React 19. Styling uses
Tailwind CSS v4 with shadcn/ui components (Radix primitives) and Lucide icons.
Server state is handled by TanStack Query, client state by zustand,
translations by next-intl, and theming by next-themes. Design tokens live in
`app/globals.css` and `theme/palette.ts`, and the palette has an automated
contrast test. The application shell is composed of `Shell`, `SideNav`,
`BottomTabBar`, `MoreSheet`, and `TopBar`.

## Accessibility

The UI targets WCAG 2.1 AA: labelled controls, keyboard navigation, and
sufficient contrast are required for every change.

## Deployment

Containers are built in CI and run behind a reverse proxy. See
